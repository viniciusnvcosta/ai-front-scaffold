# Plano 0.6.0 — os gates que não podem reprovar, e o backport dos filhos

> **Forma:** spec-driven, igual ao plano 0.5.0. A §2 é a especificação — requisitos com
> **critério de aceitação verificável**. A §3 são as tarefas, cada uma rastreada ao requisito
> que satisfaz. Nada entra em §3 sem requisito em §2; nada fica em §2 sem forma de provar.
>
> **Escopo:** o repositório `ai-front-scaffold`, mais uma tarefa de adoção nos fronts já
> gerados (§3, T7) — porque um conserto no template que ninguém adota não conserta nada.
>
> **Relação com o plano 0.5.0** (`0.5.0-integrar-branches-e-publicar.md`): este plano é **à
> parte** e **posterior**. O 0.5.0 trata de _trabalho pronto e não integrado_ (duas branches
> paradas, tag não publicada, `main`/`develop` divergentes). Este trata de _defeito que o
> template ainda entrega em todos os refs, inclusive nas duas branches paradas_. A ordem não
> é preferência: os dois planos escrevem no mesmo arquivo (`template/justfile.jinja`), e é a
> integração do 0.5.0 que **expõe** o defeito central deste — hoje ele está mascarado (§1.4).
> **0.5.0 primeiro, 0.6.0 depois.**

### 1.3 Prova literal do gate mudo

Front renderizado de `develop` (`recipe=agent`), `git init` + commit com um token falso de
formato `ghp_` + 36 alfanuméricos, `gitleaks 8.30.1` **instalado**:

```text
=== gitleaks direto ===
exit gitleaks=1
=== forma do template (template/justfile.jinja:25) ===
gitleaks not installed; skipping
exit da forma do template=0
=== forma consertada (if/else) ===
exit da forma consertada=1
```

A linha do template é `@command -v gitleaks >/dev/null && gitleaks detect --no-banner || echo
"gitleaks not installed; skipping"`. Em `A && B || C`, o `||` também dispara quando **B** falha:
"leak encontrado" (exit 1 do gitleaks) cai no `echo` e a receita sai **0**, imprimindo a
mensagem de ferramenta ausente **com a ferramenta presente**. O gate não é frágil — ele é
**mudo por construção**, e a mensagem que imprime é falsa.

Isto contradiz um invariante escrito do próprio `CLAUDE.base.md` (§4, invariante 5): _"CI fails
if a secret is detected."_ Hoje não falha.

### 1.4 Por que ninguém viu: o defeito está mascarado, e o 0.5.0 desmascara

`just lint` de um front renderizado de `develop` **morre antes** de chegar ao gitleaks:

```text
Found 25 errors.
error: Recipe `lint` failed on line 24 with exit code 1
EXIT just lint = 1
```

Linha 24 é o `ruff`. Os 25 erros são os que o plano 0.5.0 mostra já corrigidos na branch
parada. Logo, hoje o gate mudo é invisível porque o gate **anterior** sempre reprova.

Quando o 0.5.0 integrar a 0.4.0, três coisas mudam ao mesmo tempo:

1. o lint do front recém-gerado passa a estar **limpo** (`All checks passed`) — o `ruff` deixa
   de mascarar;
2. `template/.tool-versions` passa a **pinar `gitleaks 8.30.1`**, e `tools/ci-install-tools.sh`
   o instala no agente — o ramo "not installed" deixa de ser hipotético e passa a ser mentira;
3. `template/azure-pipelines.yml` roda **`just check`** como Gate bloqueante de PR — ou seja,
   `lint` (com o gitleaks mudo dentro) passa a ser a coisa que autoriza um merge.

O defeito não fica pior por acidente: ele fica pior **exatamente** quando o gate se torna
bloqueante. É o motivo de 0.6.0 vir logo atrás de 0.5.0, e não "quando der".

### 1.5 O terceiro gate que não pode reprovar: `just contracts`

`template/tests/contract_tests/test_contracts.py`, íntegro:

```python
def test_contracts_dir_exists():
    assert pathlib.Path("contracts").is_dir()
```

O diretório é renderizado pelo próprio template (com `.gitkeep`), então a asserção é verdadeira
por construção e **nunca** pode reprovar. Enquanto isso, `CLAUDE.base.md` §5 declara "contract
tests are mandatory" e o Gate da 0.4.0 conta `just contracts` como um dos quatro passos de
`just check`. Medição do custo real disso: o `meeting-notes-agent` tem **9 linhas** de teste de
contrato e **zero** schemas vendorizados — e seu `just contracts` está verde.

### 1.6 A ausência do `.dockerignore`

O `Dockerfile.jinja` faz `COPY . .` (linha 32) — deliberadamente, para que o 2º `uv sync`
instale o projeto. Sem `.dockerignore`, esse `COPY` leva para dentro de uma camada de imagem
tudo que estiver no diretório de build: `.git` inteiro (que guarda segredo já removido da
árvore), `.env` se existir, `.venv` construído no host, `.scratch`/`.claude`. Remover em camada
posterior **não apaga** da anterior. Enquanto a imagem só existia localmente isto era invisível;
as imagens dos fronts vão para o ECR desde 08/2026.

Os quatro fronts descobriram isso um a um e escreveram o arquivo à mão. O template segue sem ele
em todos os refs — logo, **todo front novo nasce com o mesmo furo**.

## 2. Especificação

### R1 — O gate de segredo do template pode reprovar

- **AC1.1** Em front renderizado de `main`, com `gitleaks` instalado e um token falso commitado,
  `just lint` sai **≠ 0**. (Baseline hoje: sai 0 — §1.3.)
- **AC1.2** Sem `gitleaks` no PATH, `just lint` **não** falha por isso na workstation, e a
  mensagem de skip vai para **stderr** (não se confunde com saída de sucesso).
- **AC1.3** Em CI, ausência de `gitleaks` **reprova** em vez de pular: o pipeline instala versão
  pinada (`.tool-versions`), então "pulou" em CI só pode significar gate perdido. Forma:
  `GITLEAKS_REQUIRED=1` no `azure-pipelines.yml`, e o `else` da receita falha quando essa
  variável está setada.
- **AC1.4** Mutação registrada: reintroduzir `&& … || echo` faz a guarda de R5 reprovar.

### R2 — Todo front nasce com contexto de build fechado

- **AC2.1** `template/.dockerignore` existe e é renderizado (o `_templates_suffix` é `.jinja`, e
  arquivo sem sufixo é copiado literalmente — não precisa de Jinja).
- **AC2.2** No front renderizado, o arquivo exclui no mínimo: `.env`, `.env.*`, `*.pem`, `*.key`,
  `.git`, `.venv`, `__pycache__`, `.pytest_cache`, `.ruff_cache`, `.scratch`, `.claude`.
- **AC2.3** Teste unitário **no front renderizado** (`tests/unit/test_dockerignore.py`) afirma
  esse conjunto mínimo — para que o filho não perca a propriedade num refactor. Mutação: remover
  `.env` do arquivo reprova o teste.
- **AC2.4** `docker build` do front renderizado continua verde e a imagem **não contém** `.git`
  nem `.env`. Proxy barato quando não há docker no agente: `docker build --no-cache` local + `find
  / -name .git -maxdepth 3` no container. A prova com docker é **humana ou de CI opcional** — o
  risco residual está registrado em §4.
- **AC2.5** O arquivo **não** exclui `README.md`, `ops/` nem `pyproject.toml`: o `HEALTHCHECK` do
  `Dockerfile` roda `ops/healthcheck.py`, e um `readme = "README.md"` futuro no `pyproject`
  faria o build do projeto falhar dentro da imagem. (A variante do `lead-enrichment-engine`
  exclui `README.md`; hoje é inofensivo porque nenhum `pyproject` declara `readme`, e é
  precisamente o tipo de detalhe que não se herda por cópia manual.)

### R3 — `uv.lock` deixa de ser ignorado, e não volta a ser

Corrigido na branch da 0.4.0; este plano garante que a correção **chega e permanece**.

- **AC3.1** `template/.gitignore` em `main` não contém `uv.lock`.
- **AC3.2** Guarda de CI do scaffold reprova se `uv.lock` reaparecer no `.gitignore` do template.
- **AC3.3** O `CHANGELOG` diz ao filho o que fazer no `just update`: commitar o `uv.lock`
  existente. Sem lock rastreado, `uv sync --frozen` do `Dockerfile` cai no fallback e o artefato
  deixa de ser reprodutível — que é o mesmo defeito que o comentário do `Dockerfile.jinja` já
  documenta em prosa (linhas 6-25).

### R4 — `just contracts` deixa de reportar verde sem verificar nada

Requisito difícil por um motivo legítimo: um front recém-nascido **não tem** contrato pinado, e o
precedente da 0.4.0 é explícito ("taggear v0.4.0 com `just lint` vermelho num projeto
recém-gerado não é aceitável"). Um gate day-one vermelho seria coerente com a verdade e
incoerente com esse precedente.

Desenho escolhido — **vacuidade visível e datada**, em vez de vacuidade silenciosa:

- O template renderiza `contracts/UNPINNED.md`: um waiver com data de geração e instrução de
  como pinar.
- `test_contracts.py` passa a ter dois casos: (a) se há ≥1 schema em `contracts/*.json`, cada um
  **carrega como JSON válido** e declara `$id`/`version`; (b) se não há schema nenhum, o teste
  **exige** o waiver e emite `warnings.warn("CONTRATOS NÃO PINADOS …")`.
- Remover o waiver **sem** pinar schema → o teste reprova (fail-closed). Pinar schema e deixar o
  waiver → o teste reprova (o waiver é para front vazio, não para front com contrato).

- **AC4.1** Front renderizado: `just contracts` verde, com a linha `CONTRATOS NÃO PINADOS`
  visível na saída.
- **AC4.2** Mutação A: apagar `contracts/UNPINNED.md` → reprova.
- **AC4.3** Mutação B: pôr um `contracts/x.json` inválido (JSON quebrado) → reprova.
- **AC4.4** Mutação C: pôr um schema válido mantendo o waiver → reprova.
- **AC4.5** O `meeting-notes-agent` — hoje 9 linhas e zero schemas — é o caso de teste real da
  adoção (T7).

### R5 — A CI do scaffold cobra o que este plano afirma

O plano 0.5.0 já endurece `.github/workflows/ci.yml` com lint e `cold-install` (R6 dele). Este
acrescenta as guardas **desta** rodada, no mesmo workflow, para não haver dois lugares.

- **AC5.1** Job novo `secret-gate`: renderiza, `git init` + commit de token falso, roda
  `just lint`, e **exige exit ≠ 0**. Se sair 0, a CI reprova.
- **AC5.2** Job novo confere `.dockerignore` do render (o conjunto mínimo de AC2.2).
- **AC5.3** Guarda de AC3.2.
- **AC5.4** Prova adversarial (o AC6.3 do 0.5.0 aplicado aqui): num commit descartável,
  reintroduzir cada defeito **um a um** e mostrar a CI vermelha; desfazer. Sem isso, os jobs
  novos podem estar passando por vacuidade — que é literalmente o defeito que este plano trata.
- **AC5.5** O token falso do job de segredo **nunca** é um segredo real, e o job não o imprime.

### R6 — A regra que fecha o laço filho → template

O defeito de §1.3 viveu em **cinco** repositórios e no template ao mesmo tempo, e foi consertado
cinco vezes sem ninguém olhar para cima. O `.dockerignore` foi escrito quatro vezes, em duas
variantes. Nenhuma das duas coisas foi negligência de alguém: **não havia regra**.

- **AC6.1** `CLAUDE.base.md` §5 (Definition of Done) ganha um item: _"Se o defeito consertado
  aqui existe também no template (`.ai-scaffold/`, `justfile`, `Dockerfile`, `ops/`, `.gitignore`,
  `.dockerignore`, `pyproject.toml`), o PR nomeia o PR upstream no `ai-front-scaffold` — ou
  registra por medição que o template não tem o defeito."_
- **AC6.2** `CLAUDE.base.md` §8 ganha a contrapartida de irmãos: _"defeito de superfície
  compartilhada é procurado nos outros fronts na mesma rodada, não na próxima"_, com a evidência

- **AC6.3** A regra é **verificável no lado do template**: a §5 do `CLAUDE.base.md` renderizado
  contém o item, e `grep` prova. (Não há como uma CI provar que um humano olhou para cima; o que

## 3. Tarefas

Ordem obrigatória: **0.5.0 inteiro** → T1 → T2 → T3 → T4 → T5 → T6 → T7.

### T1 — Consertar o gate de segredo (R1)

`template/justfile.jinja`, receita `lint`:

```make
lint:
    uv run ruff check .
    @if command -v gitleaks >/dev/null; then \
        gitleaks detect --no-banner; \
    elif [ -n "${GITLEAKS_REQUIRED:-}" ]; then \
        echo "gitleaks AUSENTE e GITLEAKS_REQUIRED setado — gate perdido" >&2; exit 1; \
    else \
        echo "gitleaks not installed; skipping" >&2; \

```

Três diferenças em relação ao conserto que os filhos já aplicaram, e cada uma tem razão: `if/else`
em vez de `&& ||` (a causa), skip em **stderr** (AC1.2), e o ramo `GITLEAKS_REQUIRED` (AC1.3 — os
filhos não têm isso; é a parte que só faz sentido no template, que é quem gera o pipeline).
Acrescentar `GITLEAKS_REQUIRED: 1` ao job de Gate em `template/azure-pipelines.yml`.

## 4. Riscos, e o que NÃO é problema

**`CLAUDE.base.md` na raiz não é cópia duplicada.** É um **symlink** para
`template/.ai-scaffold/CLAUDE.base.md` (medido: `git show HEAD:CLAUDE.base.md` devolve o caminho,
uma linha, sem newline final). Parece drift entre duas cópias e não é. Registrado porque a
correção "errada" aqui criaria a divergência que não existe.

**`template/azure-pipelines.yml` num repo GitHub está correto** — já registrado em §4 do plano
0.5.0, não se repete aqui. Idem os 25 erros de lint: são do 0.5.0, não deste plano.

**Testar este plano em `develop` dá falso verde.** Em `develop` o `ruff` reprova primeiro e o gate
mudo nunca é alcançado (§1.4). Toda medição de R1 tem de rodar sobre um render **com o lint
limpo** — ou seja, depois do 0.5.0, ou sobre um render onde o `ruff` foi satisfeito à mão. Um
"AC1.1 verde" medido em `develop` não prova nada além do ruff.

**`.dockerignore` sem docker no agente:** AC2.4 é a única prova que exige `docker build`. GitHub
Actions tem docker; o Gate do Azure dos filhos, não necessariamente. Risco residual aceito: a
propriedade fica garantida por conteúdo (AC2.2/AC2.3) e por prova humana pontual (AC2.4), não em
todo PR de todo filho.

**Excluir `tests` da imagem** é seguro para o `cold-install` (que roda no venv de um `uv sync`, não
dentro da imagem) mas quebraria qualquer front que rodasse pytest **dentro** do container.
Nenhum dos cinco faz isso hoje; se algum passar a fazer, a exclusão é a linha a revisar.

**O que este plano NÃO faz:** não toca `Dockerfile.jinja` (o 0.5.0 o reescreve; mexer nos dois
planos no mesmo arquivo é o conflito que o 0.5.0 já paga uma vez), não mexe em cobertura nem em
recipes do Director, e não reconstrói nem publica imagem de nenhum front.

**Publicação:** `gh` não está instalado nesta workstation (§1 do plano 0.5.0), então cada PR
deste plano se abre por URL de comparação do GitHub, e o merge é ato humano.

### 6.1 D2 · escopo — `detect` lê a HISTÓRIA, não a árvore

O T1 mantém `gitleaks detect --no-banner`. Medido:

| Onde está o segredo             | `detect` | `detect --no-git` | `protect --staged` |
| ------------------------------- | -------- | ----------------- | ------------------ |
| só na árvore (não adicionado)   | **0**    | 1                 | —                  |
| staged (`git add`, sem commit)  | **0**    | —                 | 1                  |
| só na história (fora da árvore) | 1        | **0**             | —                  |

**Nenhuma varredura cobre a outra.** E note a interação com AC1.1, que exige token
_"commitado"_: o critério passa com a forma história-only, enquanto o gate segue cego para o
segredo que o dev está prestes a commitar — que é o caso de uso do gate local. Um gate que só
vê a história avisa **depois** que o dano é permanente.

### 6.2 D3 · em front recém-gerado o gate é vácuo por construção

`just bootstrap` faz `test -d .git || git init` e **nenhum commit**. Nesse estado, com segredo
na árvore:

```text
INF 0 commits scanned.
INF no leaks found            → exit 0
gitleaks detect --no-git      → exit 1
```

É a janela em que o `.env` é montado e valores são colados. O gate está decorativo exatamente
ali. Isto também qualifica §1.4: depois da 0.5.0 o `ruff` para de mascarar, mas num render
fresco a varredura de história continua não tendo o que ler.

### 6.3 D4 · `-v` e `--redact` são um par — e isto é load-bearing para AC5.5

| Forma         | valor em claro na saída | diz arquivo/linha |
| ------------- | ----------------------- | ----------------- |
| (nada)        | não                     | **não**           |
| `-v`          | **sim (2×)**            | sim               |
| `-v --redact` | não (`REDACTED`)        | sim               |

Sem `-v`, a reprovação inteira é `WRN leaks found: 1`: não é acionável. Com `-v` e sem
`--redact`, o valor vai **em claro para o log de CI** — e AC5.5 ("o job não o imprime") passa a
depender de um flag que o T1 não pede. É a mesma classe do invariante 5 ("a credential must
never reach stdout/stderr") aplicada à ferramenta que deveria defendê-lo.

### 6.4 D5 · a armadilha do conserto — duas varreduras remutam o gate

Adotar as duas varreduras **separadas por `;`** dentro do `if` recria o defeito de §1.3 numa
forma nova: o `if` devolve o exit da **última** linha do ramo. Medido, segredo só na árvore:

| Forma dentro do `if`                        | exit |
| ------------------------------------------- | ---- |
| `gitleaks --no-git; gitleaks` (ponto e vírgula) | **0** |
| `gitleaks --no-git && gitleaks`              | 1    |
| shebang + `set -euo pipefail`, duas linhas   | 1    |

Vale registrar no comentário da receita: é o erro que o próximo mantenedor cometeria, e ele
volta a satisfazer AC1.1 enquanto perde AC1.1 na árvore.

### 6.5 D6 · `--config` é co-requisito, e o allowlist não é conveniência

`gitleaks detect --config .gitleaks.toml` **sem o arquivo** →
`FTL unable to load gitleaks config … no such file or directory`, exit 1. Portanto a config e o
flag entram no **mesmo commit**, ou nenhum dos dois entra: um front gerado com o flag e sem o
arquivo tem `just lint` quebrado no primeiro uso, por motivo que não é segredo nenhum.

`template/.gitleaks.toml` proposto (molde do `platform-infra`, que é o único repo da casa que
já usa `--no-git --config --redact`):

```toml
title = "{{ project_name }} — gitleaks"
[extend]
useDefault = true
[allowlist]
description = "Não-segredos e diretórios locais (valores reais vivem no secret manager)."
paths = [
  '''(^|/)\.env$''',        # gitignored por desenho; valores reais de dev reprovariam em toda workstation
  '''\.env\.example$''',
  '''(^|/)tests/''',        # fixtures com token sintético
  '''(^|/)\.scratch/''',    # notas de agente, gitignored
]
regexes = ['''change-me[-a-z0-9]*''']
```

Ressalva medida: `.scratch/` **não** está no `template/.gitignore` (só nos repos da Mobs2, por
convenção do issue-tracker). Ou o template passa a ignorá-lo, ou essa entrada fica sem par.

### 6.6 A adoção pelos filhos custa mais do que R7 supõe — e a medição surpreende

Exit do gitleaks por modo, hoje, nos cinco repos (read-only):

| Repo                     | árvore (`--no-git`) | história (`detect`) | classe do achado |
| ------------------------ | ------------------- | ------------------- | ---------------- |
| `bitrix-orchestrator`    | 0                   | 0                   | —                |
| `campaign-manager`       | **1**               | 0                   | `.env` (2)       |
| `whatsapp-sales-agent`   | **1**               | 0                   | `.env` (2)       |
| `lead-enrichment-engine` | **1**               | 0                   | `.env` (2) + `.scratch/…md` (1) |
| `platform-infra`         | 0                   | 0                   | — (já usa a forma boa) |

1. **A história está limpa nos cinco.** A varredura que falta é grátis de adotar.
2. **A varredura de árvore reprovaria 3 de 4 fronts hoje** — e **todo** achado é `.env`
   untracked e gitignored (`git ls-files .env` vazio nos três) ou nota de agente em
   `.scratch/`. **Zero vazamento commitado.** É exatamente o que o allowlist de §6.5 cobre, e é
   por isso que ele não é opcional: sem ele, ligar `--no-git` deixa 3 fronts vermelhos por
   motivo nenhum e o gate morre por irrelevância na primeira semana — o modo mais comum de um
   gate morrer, e o irmão do defeito que este plano trata.

Consequência para AC7.2: além de "`just lint` reprovando com token falso plantado", a adoção
precisa de um passo de **classificação** de qualquer reprovação preexistente como *allowlist*
(arquivo gitignored, não-vazamento) ou *incidente* (segredo commitado) — nunca remover flag
para ficar verde. Hoje, medido, os três casos são todos allowlist.

Registrar também que a varredura de história é **irreversível por natureza**: uma vez que um
segredo entre num commit, ela reprova para sempre até a história ser reescrita. Hoje é teórico
(história limpa nos cinco); quando acontecer, a resposta é rotação + resposta a incidente.

### 6.7 Forma alvo, unindo T1 a este adendo

Mantém as três diferenças do T1 (if/else, skip em stderr, `GITLEAKS_REQUIRED`) e acrescenta as
quatro metades restantes. Shebang em vez de `\`-continuation: é o idioma que a receita
`cold-install` já usa neste template, e o `set -e` remove a armadilha de §6.4 na raiz.

```make
# lint + secret scan
#
# `if/else`, não `A && B || C`: o `||` também dispara quando B falha, então "leak
# encontrado" saía 0 imprimindo "not installed" — mensagem falsa (§1.3).
#
# DUAS varreduras: `detect` lê a HISTÓRIA, `--no-git` lê a ÁRVORE, e nenhuma cobre a
# outra (§6.1). Num front recém-gerado (`just bootstrap` faz git init sem commit) a de
# história vê "0 commits" e sai 0 (§6.2). ARMADILHA: separadas por `;` dentro de um `if`,
# o exit é o da ÚLTIMA — daí o `set -e` (§6.4).
#
# `-v --redact` é um par: sem `-v` a saída não diz arquivo nem linha; com `-v` e sem
# `--redact` o valor vai em claro para o log de CI (§6.3).
#
# `--config` sem o arquivo é FTL: `.gitleaks.toml` é co-requisito, não enfeite (§6.5).
lint:
    #!/usr/bin/env bash
    set -euo pipefail
    uv run ruff check .
    if command -v gitleaks >/dev/null; then
      gitleaks detect --no-git --config .gitleaks.toml -v --redact --no-banner
      gitleaks detect          --config .gitleaks.toml -v --redact --no-banner
    elif [ -n "${GITLEAKS_REQUIRED:-}" ]; then
      echo "gitleaks AUSENTE e GITLEAKS_REQUIRED setado — gate perdido" >&2; exit 1
    else
      echo "gitleaks not installed; skipping (versão pinada em .tool-versions)" >&2
    fi
```

Custo: ~160 ms por varredura em repo pequeno. A de história cresce com o número de commits; se
incomodar, `--log-opts` limita o alcance. Não otimizar antes de medir dor.

Guardas de CI que o R5 deve exigir, além das já listadas: reprovação com segredo **só na
árvore** e **só na história** (duas mutações distintas — uma só não prova as duas varreduras),
e um caso verde com `.env` populado + fixture de teste, que é o que prova que o allowlist
funciona e a workstation não vira refém.
