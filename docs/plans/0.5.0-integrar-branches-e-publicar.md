pinasse `v0.4.0` receberia código que não existe em `main` — e, como a tag não está no
origin, um `copier update --vcs-ref v0.4.0` de outra máquina simplesmente **falha**.

**2. Os 25 erros de lint "preexistentes" já estão consertados numa branch parada.**

gerado hoje, e a cura está pronta e não integrada. É o argumento mais forte para a ordem
de merge.

Ordem obrigatória: **R1 → R3 → R5/R4 → R6 → R7**. A razão de 0.4.0 vir antes da redação
não é cronológica: é que ela cria o recipe `check` de que a redação precisa (R5), e é ela
que zera o lint (AC3.1). Invertendo, resolve-se o conflito às cegas.

## 4. Riscos, e o que NÃO é problema

**`template/azure-pipelines.yml` num repo GitHub está CORRETO.** O arquivo é para os
repos **gerados**, que vivem no Azure DevOps da Mobs2; o scaffold em si usa GitHub
Actions. São dois níveis diferentes, e "consertar" isso para GitHub Actions quebraria a
CI dos filhos. Registrado aqui porque parece um erro e não é.

**A adoção pelos fronts não é automática.** Os quatro fronts existentes pinam tag e
adotam com `just update`. Este plano os deixa aptos, não atualizados — e o
`Dockerfile` novo exige rebuild + digest novo no IaC de quem adotar.

**`gh` ausente** significa merge por interface web. Se o repo tiver proteção de branch
exigindo review, T1 e T5 param até alguém aprovar — vale conferir antes de começar.

**Risco residual em R4:** 5 das 8 receitas foram medidas verdes; 3 não. A CI da matriz é
que fecha isso, e é o motivo de T4 não poder ficar para depois de T5.
